# REST Capability Descriptors

REST API capabilities are declared in `office/catalog/apis/*.yaml`. Each operation becomes one model-callable function; the orchestrator maps its arguments into a fixed, descriptor-owned HTTP endpoint. The model never chooses the host, HTTP method, or URL path.

## Request contract

`parameters` is the JSON Schema sent to the model. `request` maps argument names to request locations:

| Mapping | Meaning |
| --- | --- |
| `request.path` | Argument name to `{placeholder}` in the root-relative operation path |
| `request.query` | Argument name to query parameter name |
| `request.headers` | Argument name to dynamic request header name; scalar text only |
| `request.body` | Argument name to JSON Pointer/object field, form field, multipart field, or binary field |

### JSON body (default)

Existing flat mappings remain unchanged. JSON Pointer destinations opt into nested objects; mapped arrays/objects can be passed as values.

```yaml
request:
  body:
    /customer/address/city: city
    /tags: tags
```

Given `{ "city": "San Francisco", "tags": ["fiction", "harbor"] }`, this produces:

```json
{
  "customer": { "address": { "city": "San Francisco" } },
  "tags": ["fiction", "harbor"]
}
```

Destinations without a leading `/` remain top-level field names for backward compatibility. JSON Pointer array construction is not supported; pass the complete array as an argument value at a field pointer.

### URL-encoded form

```yaml
request:
  body_encoding: form_urlencoded
  body:
    grant_type: grant_type
    code: authorization_code
```

Values are scalar and encoded using standard URL form encoding.

### Multipart form with a file

Binary arguments are base64 strings. `binary_fields` names the multipart destination fields whose mapped values should be base64-decoded.

```yaml
request:
  body_encoding: multipart
  body:
    caption: caption
    attachment: attachment_base64
  binary_fields: [attachment]
  body_content_type: image/png
```

The `body_content_type` is used as the uploaded file's media type; the multipart boundary/content type is generated by the HTTP client. The uploaded filename is currently `upload.bin`.

### Raw binary body

```yaml
request:
  body_encoding: raw_base64
  raw_body_argument: file_base64
  body_content_type: application/octet-stream
```

The named argument must be base64 text. Raw-body mode cannot also map `request.body` fields.

## Pagination

Pagination is opt-in and GET-only. It is bounded to at most 20 requests per capability call and shares the 16 KiB aggregate response cap.

Page-number example:

```yaml
pagination:
  mode: page
  request_parameter: page
  initial_value: 1
  has_more_pointer: /has_more
  items_pointer: /results
  max_pages: 5
```

Cursor example:

```yaml
pagination:
  mode: cursor
  request_parameter: cursor
  next_value_pointer: /next_cursor
  items_pointer: /items
  max_pages: 5
```

`items_pointer` aggregates each page's selected array into `{ "items": [...], "page_count": n, "has_more": boolean }`. Without it, the result is `{ "pages": [...], "page_count": n, "has_more": boolean }`. Repeated cursors fail instead of looping.

## Response contract

The default `response.body_encoding: auto` returns compact JSON when the body parses as JSON, otherwise text. Optional response mapping:

```yaml
response:
  select:
    booking_id: /data/booking/id
    state: /data/booking/state
  include_status: true
  headers: [X-Request-Id]
```

JSON Pointer selection returns only the named fields. Selected response headers are an explicit allowlist; authentication and cookie headers are forbidden. Other body encodings are `json`, `text`, and `base64`. Non-2xx responses return a generic HTTP-status error; their response bodies are not exposed to the model.

## Limits and safety decisions

- HTTP methods: GET, POST, PUT, PATCH, DELETE.
- Timeout: 10 seconds; redirects are disabled.
- Request body limit: 1 MiB. Base64 binary is size-checked after decoding; multipart sizing includes a conservative framing allowance.
- Response limit: 16 KiB per call, including all fetched pages.
- Dynamic header names are descriptor-validated; values must be scalar text without CR/LF. Host, framing, authorization, cookie, proxy, and `Sec-*` headers cannot be model-mapped.
- Descriptor `headers` remain fixed administrator configuration. Authentication remains in the dedicated auth configuration and cannot be overridden by dynamic headers.
- Idempotency headers are sent only when the descriptor explicitly declares `idempotency_key_header`; the orchestrator call ID is used as its value.
- No automatic redirect following, pagination beyond the configured/hard maximum, response-body leakage on HTTP errors, or unbounded binary transfer.

## Deliberate non-goals

This descriptor contract does not implement streaming request bodies, arbitrary multipart filenames/per-part headers, XML/form-data response parsing, automatic pagination inference, response transformation languages, or caller-controlled hosts. Add these only for a concrete API integration with focused limits and tests.
